# 1万ページでの計測

`SPEC.md`「性能」の条件（ページが1万件・合計64MB程度）で、解析・索引・リンクの解決・検索・起動にかかる時間を測った。合成データと計測の手順は `perf/` にあり、`npm run perf`（Node.js）と `npm run perf:e2e`（Chromium）で再現できる。

## 計測の条件

| 項目 | 値 |
| --- | --- |
| 日付 | 2026-09-27 |
| 機械 | Intel Core Ultra 5 125H、メモリ15GB、Windows 11 |
| Node.js | 22.17.0 |
| ブラウザ | Playwright の Chromium（`npm run perf:e2e`） |
| 合成データ | 10,000ページ、63.8MB。`perf/synth.ts` が seed 1 で作る |
| リンク | 合計 206,342、1ページ平均 20.6。`[[name]]` 70%、`[[title]]` 20%、まだないページ 10%。front matter の `tags` と `#タグ` を含む |
| ページの長さ | 平均 6.4KB。短いページが多く、まれに長いページがある散らし方 |
| 重複するH1 | 約5%。H1のないページ 約5% |

合成データのリンク密度（1ページ20本）は実際のノートより多い。実際のノートで測り直すまでは、リンクに比例する数字（索引の構築、2 hop link）は上限の目安として読む。

## 結果: 解析2秒、索引の構築0.3秒、2回目の起動2秒、検索0.2秒

Node.js（`npm run perf`）。5回の中央値。

| 処理 | 時間 |
| --- | --- |
| `parsePage` 全件（64MB） | 2.0〜2.2秒（初回だけ1.1秒。2回目以降はGCが入る） |
| `KbIndex` の構築（解析済みのページから） | 0.3秒 |
| 解析＋構築（控えから索引を作り直す分） | 2.3秒 |
| `resolve`（name / title） | 1µs |
| `backlinks` | 14µs（最多の205件でも0.1ms） |
| `twoHop`（平均20リンク） | 1.0ms |
| 素朴な全文検索（AND、300件で打ち切り） | 170〜200ms。本文を小文字にしておいても変わらない（`includes` で64MBを走査する分が本体） |
| ヒープ | 146MB（中身64MBを含む） |

Chromium（`npm run perf:e2e`）。ローカルモードの `/api/*` から読む。

| 処理 | 時間 |
| --- | --- |
| 初回の起動 | 取り込み（一覧＋1万件の `GET /api/pages/<path>`、同時8件）26.6秒、解析＋索引1.3〜1.6秒。ページ全体では29〜52秒で、差は取り込みでも解析でもない部分にあり、原因は未確認（生成直後のファイルへのウイルススキャンと推測） |
| 2回目の起動 | 3.8〜4.5秒。うち `sync` 2.0〜2.4秒、解析＋索引1.2〜1.5秒 |
| 2回目の `sync` の内訳 | `GET /api/pages` 2.0秒（ローカルモードが1万ファイルのSHAを計算する分。本番ではGitHub側の応答時間になる）と IndexedDB の `getAll` 0.6〜0.9秒（64MB）。二つは同時に走るので `sync` は長いほうの時間になる |

## 目標との比較

| 目標（`SPEC.md`） | 結果 | 判定 |
| --- | --- | --- |
| 初回の索引作成は数秒まで | 解析＋索引 1.3〜2.3秒 | 収まる。取り込みの26秒は1万回のAPI呼び出しの分で、段階6で tarball にすると変わる |
| 2回目以降の起動 100ms | 約2秒（IndexedDB から64MBを読む0.6〜0.9秒＋解析と索引1.3秒）。解析済みのページから `KbIndex` を作るだけでも0.3秒 | 収まらない |
| ページの表示 100ms | 解決・バックリンク・2 hop link で合計1ms程度 | 収まる見込み。Markdownの変換（marked、Mermaid）は段階3で測る |
| 検索 100ms | 全文の走査で170〜200ms | 収まらない |

## 分かったことと次にすること

2回目以降の起動は、64MBの本文を IndexedDB から読むだけで目標の6倍、解析と索引作りでさらに13倍かかる。本文を読まず、解析結果（`title`・`links`・`created`・`updated`）だけを読んで索引を作り、差分の取得はその後に回す形に変える（`DECISIONS.md` 2026-09-27「起動時は解析結果だけを読む」）。本文は、ページの表示ではそのページだけを、検索では初めて検索したときに全件を読む。解析済みのページから `KbIndex` を作るだけでも0.3秒かかり、その大半は20万本のリンクの逆引き（Set への追加）なので、逆引きは最初の描画の後に作ってよいことにした。解析結果のレコードは本文抜きで約6.6MB、Node.js で `JSON.parse` に20〜27ms、`structuredClone` に47〜56msかかる（Chromium の IndexedDB からの読み出しは次のタスクで測る）。

検索は、本文の走査だけで目標を超える。段階3ではまず走査で作り、検索欄の入力に対して結果が返るまでの体感で判断する。遅ければ `TODO.md`「完成後」の trigram 索引を前に出す。

解析は、最初の計測では6.4秒かかっていた。コードの塗りつぶし（`maskCode`）をH1とリンクで2回行っていたのを1回にし、インラインコードの探索で1文字ずつ連結していたのをまとめて写すようにして、1.1〜2.0秒になった。

ローカルモードの `GET /api/pages` は1万ファイルを同時に開いて `EMFILE` で落ちたので、同時に開く数を64に抑えた。

## 解析結果だけを読む形にした後の2回目の起動: open 61ms

起動時は控えの解析結果のレコードだけを読んで索引を作り、リンク（20万本）はレコードから分けて置いて最初の描画の後に読み、差分はその後に取る形にして測り直した（同じ日、同じ機械と合成データ）。`npm run perf:e2e` の2回目の起動5回の中央値。

| 処理 | 時間 |
| --- | --- |
| `open`（IndexedDB を開いてから `name`・`title` で引ける索引ができるまで） | 61ms（53〜63ms。1回だけ141ms）。うちレコードを読む40ms、索引を作る19ms |
| `reverse`（リンクを読んで逆引きを作る。描画の後） | 217ms |
| `sync`（差分の取得。`GET /api/pages` がローカルモードで1.9秒） | 1.9秒 |
| IndexedDB の内訳 | 解析結果のレコード（2.0M文字）の `get` 28ms、`JSON.parse` 15ms。本文1件の `get` 1〜3ms。本文全件の `getAll` 0.9秒 |

`SPEC.md` の「2回目以降の起動 100ms」は、この計り方で収まる。途中の試みとして、リンクを含めた一つのレコード（4.9M文字）では読むのに110ms、索引を作るのに28msで `open` が139msだった。オブジェクトのまま `structuredClone` で置いても JSON 文字列で置いても差はなく、量を減らすしかなかったので、リンクを分けた。

ページの表示に要る本文は1件1〜3msで読める。検索で全件の本文を読むのに0.9秒かかるので、段階3では最初の検索のときに読んで以後は持っておく。
